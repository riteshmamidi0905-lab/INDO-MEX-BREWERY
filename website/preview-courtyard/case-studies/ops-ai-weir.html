Engineering case study

Putting the Ops AI behind THE WEIR gateway

Two authorization layers that do not trust each other, joined by one audit key.

Layers

THE WEIR decides first: per-tool policy, results labelled internal, egress denied, writes need approval, tamper-evident audit chain. Only forwarded calls reach the Ops AI gate, which applies its own role and site rules.

Audit join

WEIR events carry a 16-hex prefix of the call hash. The upstream recomputes the same hash from the exact tool name and arguments, so each WEIR decision can be matched to the Ops AI audit row it caused, or shown to have been blocked first.

Behaviours tested

Allowed read equals the direct answer; unknown tools never reach the Ops layer; after a warehouse read an egress tool is refused; a site manager's out-of-scope request is allowed by WEIR but denied by the Ops layer; write tools need approval and nothing executes while pending.

Evidence

lab/nasha_lab/warehouse/ops_ai_weir.py, tests/test_ops_ai_weir.py (4 tests against the real gateway).

Limits and what is not claimed. One gateway per principal; the WEIR package is a separate repository and must be installed; in-process only; no language model.
NASHA is a concept and a synthetic lab: no customers, no revenue, no production deployment. Code written with AI assistance; the author's own understanding is tested separately.
