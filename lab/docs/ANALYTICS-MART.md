# NASHA analytics mart (P4): design and how to run

**SYNTHETIC DATA / SIMULATED OPERATION / NOT PRODUCTION DEPLOYED.** NASHA has no restaurant, customers, sales, suppliers or staff. Prices, costs and recipes are placeholders or assumptions. Nothing here is a business result.

A reproducible star schema, metric layer, SQL library, data-quality framework, forecasting backtest and simulated experiment, built from the lab's synthetic generator. Additive: nothing in the frozen Block 3 evidence was changed. Evaluation numbers are in [ANALYTICS-EVALUATION](ANALYTICS-EVALUATION.md); the decision memo is [ANALYTICS-EXEC-MEMO](ANALYTICS-EXEC-MEMO.md).

## Star schema (text diagram)

```
                               dim_date            dim_site            dim_channel
                                  |                   |                    |
dim_guest(SYNTH) --- fact_order (grain: accepted order) ---------------------+
                          |
dim_menu_item (SCD2) --- fact_order_line (grain: order line) --- dim_site, dim_date, dim_channel, dim_guest
        |
bridge_item_ingredient (recipe per item VERSION) --> dim_ingredient <-- fact_usage_daily (site x ingredient x date, derived)
                                                          |
                    fact_inventory_snapshot (site x ingredient x weekly count) -- dim_site, dim_date
                    fact_po_line (PO line) -- dim_supplier, dim_site, dim_ingredient, dim_date (order / expected / received)
                    fact_waste_adjustment (event) -- dim_waste_reason, dim_site, dim_ingredient, dim_date
                    fact_quality_finding (lab DQ finding) -- dim_dq_rule, dim_site
                    fact_exception_event (inventory exception workflow, SIMULATED stages)
```

Conformed dimensions: date, site, menu item, supplier, ingredient (shared by several facts). Surrogate keys everywhere; key 0 is the Unknown member of each dimension so facts never lose rows. Full DDL and grain comments: `lab/analytics/sql/ddl.sql`.

### SCD Type 2 (menu item)

`dim_menu_item` has one row per (item_id, version) with `valid_from` inclusive and `valid_to` exclusive; open rows end `9999-12-31`; exactly one `is_current` row per item. Facts carry the **version in effect on the order date** (`item_key`), so the old name stays on old orders. Tests check no gaps, no overlaps, one current row and that every order line falls inside its version window (0 violations in this build).

## How to run

```bash
cd lab
python3 -m analytics.mart --db /tmp/nasha_mart.sqlite     # build the mart (seed 1) and print row counts
python3 -m analytics.run_all                              # regenerate every file in lab/results/analytics/ (~1 minute)
python3 -m analytics.render_docs                          # re-render the ANALYTICS-*.md docs and the dashboard from those files
python3 -m pytest -q -p no:cacheprovider tests/test_analytics_*.py
python3 -m pytest -q -p no:cacheprovider tests            # full suite (about 2 minutes)
```

Everything is seeded; `config.py` holds every assumption and `config_hash` is stamped in each results file. SQLite is the engine (3.45 here); DDL and loads are portable SQL, with SQLite-specific `date()`, `julianday()`, `GROUP_CONCAT`, `rowid` and `ATTACH`-free `backup()` noted in the query headers. Dependencies beyond the lab's: none (numpy and scipy come with scikit-learn).
