# NASHA AI — Engineering status and implementation boundaries

**Synthetic prototype only.** NASHA has no operating brewery, sales, customers, procurement contracts, or commercial deployment. THE WEIR is a deterministic MCP information-flow security gateway, **not** a NASHA business unit.

## Role architecture

Twelve role definitions live in `nasha_lab/ai_team.py`; they describe purposes, data, dependencies, tools, permissions, review boundaries, metrics and failure handling. They are **not** twelve deployed autonomous agents. The existing LangGraph operations agent is the only existing NASHA stateful agent runtime; inventory, DQ, policy, retrieval and evaluation remain deterministic services. `nasha_lab/ai_workflows.py` adds reproducible **plan-only** cross-role handoffs for seasonal beer development, inventory/procurement, and synthetic feedback/marketing.

## Security boundary

No workflow planner invokes a protected tool. A planned procurement or campaign is not execution or approval. Existing NASHA local identity/grants and THE WEIR are **not interchangeable**. Actual cross-repository enforcement requires connecting NASHA's tool dispatch to THE WEIR's real `Gateway.call_tool_detailed` with declared upstream tools, a pinned policy, durable approval store and negative end-to-end tests. Until that path is exercised in CI, label the integration **NOT VERIFIED**. No human approval may be inferred from a planner output.

## Visual system (design specification, not generated assets)

Use dark basalt and warm brass NASHA surfaces with restrained accent colors from `ai_team.ROLES`. Symbols are abstract, geometric glyph concepts rather than robot mascots. Accessible agent cards should show name, classification, responsibilities, input/output contract, dependency, actual implementation status, and a visible approval boundary. Any diagrams should label THE WEIR as an external independent gateway. No image files or portfolio preview have been generated by this specification.

## Reproduction

From `lab/` after installing `requirements-dev.txt`:

```bash
python -m pytest -q tests/test_ai_team.py tests/test_ai_workflows.py tests/test_duplicate_triage.py tests/test_release_gate.py
python -m pytest -q tests
python -m nasha_lab.export_portfolio --check
python -m nasha_lab.evaluate v1
```

The CI workflow also runs the exporter three times, hashes the serialized payloads, checks historical evidence, and tests Docker. Results must be taken from the corresponding completed workflow; a successful earlier workflow is not evidence for later commits.

## Next acceptance blockers

1. THE WEIR must actually mediate NASHA tool execution, including scoped one-use approvals, expiration, missing-policy denial, and audit correlation.
2. The three business workflows must execute real typed service calls through existing runtime rather than merely emit plans; add goldens and failure-injection tests.
3. Implement and test cross-system trace correlation and incident reconstruction with secret-safe payload handling.
4. Build a separate, accessible portfolio development preview after inspecting existing site code. **Never publish automatically.**
5. Stage LinkedIn content and diagrams for review; do not publish.

**Truth boundary:** Historical DQ baseline is preserved. Ambiguous near-duplicate candidate triage is review-only; clean synthetic negative tests do not prove real-world false-positive rates.
