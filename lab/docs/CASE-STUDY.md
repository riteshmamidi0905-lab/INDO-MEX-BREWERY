# Case study: does adding an LLM actually improve a human-supervised operations agent?

> I built a simulated enterprise environment with synthetic operations data, status-aware company knowledge, typed tools, human approval and tracing. Then I built two operations planners behind one interface, a deterministic one and a local-LLM one, and evaluated them under identical permissions, scenarios and metrics, rather than assuming the LLM was better.

**Disclosure.** SYNTHETIC DATA / SIMULATED OPERATION / OFFLINE EVALUATION / NOT PRODUCTION DEPLOYED. NASHA is an independent founder concept: there is no restaurant, no customer, no supplier and no sale. All numbers come from deterministic synthetic scenarios and author-written question sets, with the same person writing the system and the tests. Compute cost: LOCAL COMPUTE - NO API CHARGE (free CPU runners, open-weight models, no paid API).

## Problem
An operations assistant that can read inventory, orders and policy is useful only if it (1) does not act on bad data, (2) does not treat a draft, superseded or unverified document as policy, (3) says "insufficient verified evidence" when that is true, and (4) cannot spend money or message a supplier. The domain adds a hard constraint: a founder's no-beef/no-pork rule (D-54) where "probably fine" is the wrong answer.

## What was built
Synthetic operations platform -> status-aware knowledge layer over the real project documents (decision register, authority classes, supersession) -> 18 typed tools in five permission classes -> FastAPI and MCP surfaces (a trusted NASHA MCP server and an untrusted failure-injection server behind a trust gateway) -> LangGraph agent that proposes, interrupts for a human, resumes from a checkpoint and records a full trace -> signed reviewer identity (roles, expiring tokens, per-action grants bound to exact arguments) -> small accessible review console. Architecture: [ARCHITECTURE.md](ARCHITECTURE.md), [AGENT.md](AGENT.md), [THREAT-MODEL.md](THREAT-MODEL.md).

## The experiment
**Planner question.** One `Planner` interface; `DeterministicPlanner` (control) and `LLMPlanner` run on the same state, tools, permissions, approval, trace and metrics. The model only proposes; deterministic code validates, authorizes, executes and traces. 259 generated scenarios in four splits (dev 67, held-out 75, held-out B 75, adversarial 42); real models run on a stratified subset because CPU inference is slow. Method and caveats: [PLANNER-EXPERIMENT.md](PLANNER-EXPERIMENT.md).

**Retrieval question.** BM25, TF-IDF/LSA, hybrid, static neural embeddings (spaCy 300-d), a sentence encoder (all-MiniLM-L6-v2) and hybrids, plus the same vectors in PostgreSQL/pgvector with HNSW, on 467 questions in 13 categories (dev/held-out, per-category and per-source reporting). Details: [RETRIEVAL-EVALUATION.md](RETRIEVAL-EVALUATION.md).

## Results (reproducible; real-model numbers recovered from CI logs)
- **The deterministic planner won.** It passed 259/259 scenarios (held-out B, never inspected before scoring, 75/75). Real local LLMs (Qwen2.5-1.5B-Instruct, Apache-2.0, CPU, JSON-schema constrained) passed **9/138 and 5/140 (3.6-6.5%)** in two runs under the same strict checks, with correct action in 37% and required evidence tools called in ~15%; median latency ~30 s vs 47 ms. The deterministic planner won on 122 scenarios the model lost; the model won on none (also against the 7B model). A 7B model (Qwen2.5-7B-Instruct, one scenario per family on held-out B + adversarial) passed 10/35 (29%) with no silent all-clears and no forbidden attempts, but 152 s median latency on CPU; every pass was a single-obvious-action scenario. Scale narrows the gap; it does not close it.
- **The raw small model produced the dangerous failure silently.** It answered `NO_ACTION` when action was needed in 30 of 140 scenarios (21%); the deterministic evidence envelope removed all of them.
- **The safety architecture held against a real model.** ~1,000 model calls across three runs, 95-119 forbidden-action attempts per 1.5B run (unknown tools, mutations, external actions, invented targets), **0 executed, 100% approval-boundary compliance**. At most 3.7% of calls violated the output schema, so the problem was tool choice, not JSON.
- **A deterministic guardrail is a safety device, not a capability.** Overriding unsafe or unsupported model actions with an evidence envelope kept the system safe but cut abstention accuracy (79% -> 37%) because a model that gathers little evidence leaves the envelope with only "escalate".
- **Neural embeddings did not justify their complexity here.** MRR: BM25 0.913, MiniLM 0.672, BM25+MiniLM hybrid 0.842, static spaCy vectors 0.259. MiniLM is weakest exactly where the corpus is identifier-driven (DECISION_STATUS .29, SUPERSEDED .36, NUMERIC .24 vs BM25 .85/.84/.84). pgvector worked (HNSW, cosine) and matched the exact scan to three decimals at 758 chunks; it is not needed at this size.
- **Abstention improved but is not solved.** A learned gate over 14 retrieval features, combined with the built-in rules, cut held-out false answers from 29% to 15% (19/66 -> 10/66) at the cost of false abstentions 2% -> 6%; behaviour on hand-written paraphrases is mixed and small-n, reported as unsettled.
- **Engineering evidence.** 229 tests pass in CI (unit, API, MCP, trust boundary, LangGraph, identity, UI accessibility + XSS, property-based); mutation testing of the safety code killed 22 of 22 mutants after fixing a weak-test finding; the Docker image builds and serves in CI; deterministic experiments reproduce byte-for-byte in CI.

## The failure that mattered
"Grounded" had come to mean "the model said so": the check that a proposed mutation targets a real record accepted keys that appeared only in the model's own tool arguments. The worst-case stand-in found it; the fix grounds only in trusted, successful tool results; the lesson from mutation testing was that two redundant defences had been masking each other's missing tests. Full story with root cause, fix, regression tests and remaining limitation: [FAILURE-STORY.md](FAILURE-STORY.md). Earlier: a failed supplier lookup silently became `NO_ACTION` in Block 2 ([../results/FAILURE-LOG.md](../results/FAILURE-LOG.md)).

## Limitations (stated up front)
Synthetic data and same-author evaluation (generated questions copy corpus wording, which flatters lexical retrieval; scenario expectations were built by the same author as the control planner; two of four scenario splits are contaminated for the deterministic planner). Real-model runs use small CPU-friendly models on a stratified subset; no larger model, prompt tuning, re-ranker or fine-tuning was tried, so "the LLM lost" is a statement about these models and this harness, not about LLMs. The injection detector is a regex plus a taint check. Auth is a local demo identity, not a production identity provider. Docker is verified in CI. None of this is evidence of results in a real business.
