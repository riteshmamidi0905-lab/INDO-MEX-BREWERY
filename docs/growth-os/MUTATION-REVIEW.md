# Growth OS workflow mutants: what each one really measures

Source: `lab/tests/test_growth_workflow_eval.py`. Mutants are **test-only patches** (`unittest.mock`, or privileged SQL on a throwaway schema). No production control was weakened or made configurable to make a mutant detectable. Every probe passes on the unmutated system (8 tests) and fails under its mutant (8 tests).

Honest reading: several mutants must disable more than one layer, because the system is defended in depth and removing one layer is *correctly* not enough to cause the failure. Where that is so, a separate test proves the remaining layer works alone.

| # | Property | What the mutant disables | Further defenses that had to be disabled for the failure to appear | Independent test that the remaining defense works |
|---|---|---|---|---|
| 1 | Authorization: a VIEWER cannot cause a CRM update | THE WEIR role policy (`INITIATE_ROLES`, `READ_ROLES`) | Service role policy `lead.qualify` (the CRM write is also refused there); the workflow's own role gate reads the same constants so it is disabled too | `test_a_viewer_allowed_by_THE_WEIR_alone_is_still_stopped_by_the_service_policy`; `test_roles_without_the_write_tool_are_denied_by_the_weir_and_viewer_is_denied_earlier`; `test_direct_crm_writes_by_unauthorised_roles_are_denied_and_audited` |
| 2 | Tenant isolation: tenant A cannot read B's lead | PostgreSQL RLS on leads/contacts/accounts AND the tenant filter in the query | Per-tenant sessions and signing keys, the workflow's tenant-filtered lead check, composite tenant foreign keys (not touched by this probe, which reads at service level) | `test_cross_tenant_sessions_leads_runs_and_approvals_do_not_cross`; `test_cross_tenant_probes_across_every_table_return_nothing`; control mutant "RLS disabled" in `test_growth_mutations.py`. Limit: this probe does not exercise the HTTP path. |
| 3 | Correct qualification | Score threshold (60 -> 40) | The independent validator (recomputes points with separate arithmetic) | `test_a_wrong_threshold_alone_is_caught_by_the_independent_validator` (threshold change alone yields `VALIDATION_FAILED`, no approval, no CRM write); the five-case hand oracle |
| 4 | Suppression bypass | The reader reports no suppression (used both at run time and at execution time, since both read the same context) | The suppression-sets-opt_out rule: the probe plants the suppression row directly so the consent flag does not also block | `test_a_suppressed_contact_is_blocked_before_any_proposal_exists`; `test_suppression_after_the_proposal_blocks_the_execution`; foundation tests for the draft gate |
| 5 | Consent bypass | `outreach_allowed` is forced true | Nothing else needs disabling: it is an advisory field. The workflow sends nothing in any case; real consent enforcement is the service draft gate | `test_a_wrongly_permissive_consent_flag_does_not_make_the_workflow_able_to_send_anything` (draft is still `Blocked`, zero activities); `test_growth_mutations.py` "consent check removed". Honest limit: this mutant measures flag correctness, not a send path, because none exists. |
| 6 | Approval single use | THE WEIR's `consume_approval` never marks an approval consumed | The workflow state machine (EXECUTED -> `APPROVAL_REPLAY`), the run-state check on direct execution, and the CRM's per-run idempotency are *not* disabled; the probe replays at the gateway level to expose the WEIR property specifically | `test_a_replayed_approval_creates_nothing_new_even_if_THE_WEIR_never_consumes_approvals` (end to end, still exactly one CRM update); `test_a_replayed_approval_creates_nothing_new` |
| 7 | CRM state transition | The CRM write's version / converted / idempotency checks | The upstream's stale-version pre-check is *not* disabled by the probe, which therefore calls the write at service level | `test_a_stale_proposal_is_stopped_before_the_write_even_if_the_service_check_is_removed`; `test_a_lead_changed_after_the_proposal_makes_it_stale`; foundation stage-graph test for opportunities |
| 8 | Audit completeness | The audit write for `lead.qualification_applied` | Database append-only privileges and the hash chain are not removed (they protect existing rows, not missing ones) | `test_every_successful_write_has_exactly_one_audit_row` (other actions); `test_audit_is_hash_chained_complete_and_tamper_evident`; the workflow trace also records the approval and the execution. Limit: no test makes the *database* refuse a CRM update that lacks an audit row; the audit is written in the same transaction by the service. |

## Residual weaknesses (not hidden)
* #2 and #8 are service-level probes; there is no test that removes the database's own refusal to write a lead without an audit row, because that coupling is by transaction, not by constraint. A trigger-enforced guarantee would be a real improvement and a candidate next step.
* #5 measures a flag, not a send path (none exists, by schema design).
* Mutants are hand-written; they show these probes detect these faults, not that no other fault exists.
