# Growth OS workflow mutants: what each one really measures

Source: `lab/tests/test_growth_workflow_eval.py`. Mutants are **test-only patches** (`unittest.mock`, or privileged SQL on a throwaway schema). No production control was weakened or made configurable to make a mutant detectable. Every probe passes on the unmutated system (8 tests) and fails under its mutant (8 tests).

Honest reading: several mutants must disable more than one layer, because the system is defended in depth and removing one layer is *correctly* not enough to cause the failure. Where that is so, a separate test proves the remaining layer works alone.

| # | Property | What the mutant disables | Further defenses that had to be disabled for the failure to appear | Independent test that the remaining defense works |
|---|---|---|---|---|
| 1 | Authorization: a VIEWER cannot cause a CRM update | THE WEIR role policy (`INITIATE_ROLES`, `READ_ROLES`) | Service role policy `lead.qualify` (the CRM write is also refused there); the workflow's own role gate reads the same constants so it is disabled too | `test_a_viewer_allowed_by_THE_WEIR_alone_is_still_stopped_by_the_service_policy`; `test_roles_without_the_write_tool_are_denied_by_the_weir_and_viewer_is_denied_earlier`; `test_direct_crm_writes_by_unauthorised_roles_are_denied_and_audited` |
| 2 | Tenant isolation: tenant A cannot read B's lead | PostgreSQL RLS on leads/contacts/accounts AND the tenant filter in the query | Per-tenant sessions and signing keys, the workflow's tenant-filtered lead check, composite tenant foreign keys (not touched by this probe, which reads at service level) | `test_cross_tenant_sessions_leads_runs_and_approvals_do_not_cross`; `test_cross_tenant_probes_across_every_table_return_nothing`; control mutant "RLS disabled" in `test_growth_mutations.py`. Limit: this probe does not exercise the HTTP path. |
| 3 | Correct qualification | Score threshold (60 -> 40) | The independent validator (recomputes points with separate arithmetic) | `test_a_wrong_threshold_alone_is_caught_by_the_independent_validator` (threshold change alone yields `VALIDATION_FAILED`, no approval, no CRM write); the five-case hand oracle |
| 4 | Suppression bypass | The reader reports no suppression (used both at run time and at execution time, since both read the same context) | The suppression-sets-opt_out rule: the probe plants the suppression row directly so the consent flag does not also block | `test_a_suppressed_contact_is_blocked_before_any_proposal_exists`; `test_suppression_after_the_proposal_blocks_the_execution`; foundation tests for the draft gate |
| 5 | Consent bypass | `outreach_allowed` is forced true | Nothing else needs disabling: it is an advisory field. The workflow sends nothing in any case; real consent enforcement is the service draft gate | `test_a_wrongly_permissive_consent_flag_does_not_make_the_workflow_able_to_send_anything` (draft is still `Blocked`, zero activities); `test_growth_mutations.py` "consent check removed". Honest limit: this mutant measures flag correctness, not a send path, because none exists. |
| 6 | Approval single use | THE WEIR's `consume_approval` never marks an approval consumed | The workflow state machine (EXECUTED -> `APPROVAL_REPLAY`), the run-state check on direct execution, and the CRM's per-run idempotency are *not* disabled; the probe replays at the gateway level to expose the WEIR property specifically | `test_a_replayed_approval_creates_nothing_new_even_if_THE_WEIR_never_consumes_approvals` (end to end, still exactly one CRM update); `test_a_replayed_approval_creates_nothing_new` |
| 7 | CRM state transition | The CRM write's version / converted / idempotency checks | The upstream's stale-version pre-check is *not* disabled by the probe, which therefore calls the write at service level | `test_a_stale_proposal_is_stopped_before_the_write_even_if_the_service_check_is_removed`; `test_a_lead_changed_after_the_proposal_makes_it_stale`; foundation stage-graph test for opportunities |
| 8 | Audit completeness (the service's audit write) | The audit write for `lead.qualification_applied` | The database audit guard (migration 108) is NOT disabled by this mutant: with it enabled the mutated write is refused and rolled back at commit (so exploitation is blocked); the probe still detects that the service-level audit write is missing | `test_every_successful_write_has_exactly_one_audit_row` (other actions); `test_audit_is_hash_chained_complete_and_tamper_evident`; the workflow trace also records the approval and the execution. `test_growth_audit_guarantee.py` (raw unaudited writes to every guarded table are refused; rollback, partial-failure, concurrency and duplicate-request tests) and control mutant "audit guard dropped". |

## Residual weaknesses (not hidden)
* #2 is a service-level probe. The former gap for #8 is closed by the deferred audit guard (migration 108). Limit of that guard: evidence must name the changed row and come from the same transaction, but the application role can write its own audit row, so a hand-written row is *detectable* (it breaks the hash chain, tested) rather than impossible.
* #5 measures a flag, not a send path (none exists, by schema design).
* Mutants are hand-written; they show these probes detect these faults, not that no other fault exists.

## Launch workflow mutants (`lab/tests/test_growth_launch_eval.py`)
Same method: each mutant removes one control, its probe must pass on the real system and fail under the mutant.

| # | Property | What the mutant changes | Layer targeted | Why one removed layer may not suffice / what else is disabled | Independent test of the remaining defense |
|---|---|---|---|---|---|
| 1 | A fabricated agent claim cannot enter the research brief | `verify_claims` always returns no problems | Independent claim verification | The platform's own verification is a second layer, but the probe's lie is built to pass it (supplied evidence contains the false number). The recommendation numbers are unaffected either way: they never come from agent text | `test_the_agent_never_changes_the_numbers_...`, `test_a_fabricated_agent_claim_is_rejected_...` |
| 2 | Recommendation = cheapest valid whole-pack quote | Comparison picks the MOST expensive quote AND the re-derivation is removed | Deterministic comparison + independent re-derivation | Both must go: with only the comparison broken the re-derivation catches it (`VERIFICATION_FAILED`) | `test_the_recommendation_equals_an_independent_recomputation_from_the_raw_tables` (raw SQL oracle) |
| 3 | Expired quotes are never used | `_valid` ignores validity dates | Quote validity | At approval time the proposal fingerprint is recomputed from current data, which would also expose a changed plan (separate probe 4) | `test_expired_quotes_are_excluded_...`, `test_quotes_that_change_or_expire_after_the_proposal_...` |
| 4 | A proposal whose quotes changed is not recorded | The fingerprint is a constant | Stale-proposal check at execution | The approved call hash in THE WEIR still binds `proposal_hash`, but the hash is stored with the proposal, so a constant passes both: the probe therefore also needs the numbers to differ at execution | `test_quotes_that_change_or_expire_after_the_proposal_make_it_stale...` (real digest) |
| 5 | A recorded recommendation has an audit row | The audit write for `procurement.record` is dropped | Service audit | With the database guard enabled the state change to EXECUTED is refused (no evidence), so the recording FAILS and nothing is recorded: exploitation is blocked, the probe detects the missing audit | `test_the_database_refuses_an_executed_recommendation_without_audit_evidence` |
| 6 | An approval cannot be used twice | THE WEIR never marks approvals consumed | THE WEIR single use | The workflow state machine and the idempotent recording still stop a replay end to end (tested for lead qualification; the probe replays at gateway level) | `test_replay_modified_proposal_expiry_and_duplicates` |
| 7 | Only OWNER/ANALYST can get a recommendation recorded | SALES added to THE WEIR roles and to the service policy | THE WEIR role policy AND service policy | Both layers are disabled; with only THE WEIR changed the service policy still refuses | `test_who_may_start_and_who_may_approve` |
| 8 | Supplier contact details cannot be stored | The database CHECK is dropped | Schema constraint | The API model also lacks a contact field beyond a short text; both must go for an e-mail to be stored through HTTP | `test_the_schema_refuses_invented_contacts_...`, `test_supplier_api_refuses_invented_contacts_...` |

Unverified: a real language-model provider has never been run, so no mutant concerns model behaviour; the agent's contribution is bounded by design (read-only tools, verified brief, no influence on numbers).
