# Milestone 4: verified intelligence, supplier research and the end-to-end entrepreneur workflow

Everything below is synthetic or labelled as what it is. No model was run, no supplier was contacted, nothing was ordered, no money was spent. Recorded results live in `lab/portfolio/growth-os-evidence.json` (`m4`).

## 1. Real-model integration: status and what is built
**Status: no language model has executed. Model-backed integration is NOT claimed.** The release gate stays REQUIRES_REVIEW for this reason.

Runtime probe (this environment): no Ollama or other local runtime reachable at `localhost:11434`; no model weights; Hugging Face unreachable (proxy refusal); no provider API key configured for the project. The Anthropic base URL in the environment is this coding session's own inference route, not a resource the project may bill against, and it was not used. Hosted providers (`openai`, `anthropic`) cost money and need explicit approval: `model_boundary.provider_permitted` refuses them **before any settings, container or network call exists** unless a person sets `NASHA_ALLOW_PAID_MODEL=1`.

Smallest safe path to a real model (already in the platform, pin f8ba373): the `ollama` provider (local, free) selected with `agent_provider="ollama"`. Nothing else changes: the same engine, the same read-only tools (`search_corpus`, `calculator`), the same boundary.

What was built so that path is safe when it is taken (`growth/model_boundary.py`, 10 rules):
* **Structured output**: the report must be `{answer, claims[{text, evidence_ids[]}], limitations[]}` within size limits, else `MALFORMED`.
* **Source grounding**: every claim cites existing evidence (`NO_EVIDENCE`, `UNKNOWN_EVIDENCE`); every number in a claim must appear in the cited passage (`UNSUPPORTED_NUMBER`); every dollar amount must equal a stored unit price or stored minimum order (`PRICE_MISMATCH`); a named supplier must be cited from its own record (`WRONG_SOURCE`); a supplier not in the directory is refused (`UNKNOWN_SUPPLIER`).
* **No overreach**: "verified" only for a verified record (`UNSUPPORTED_VERIFICATION`); the model may not recommend (`UNSUPPORTED_RECOMMENDATION`): the recommendation is computed from stored quotes and re-derived by `procurement.check_plan`.
* **Injection and tools**: instruction-like text is refused (`INSTRUCTION_TEXT`); any tool outside the read-only allowlist is refused (`TOOL_NOT_ALLOWED`).
* **Explicit uncertainty**, computed from the stored records the claims rest on (unverified leads, synthetic prices, missing prices, freshness, and a standing "nothing has been confirmed with any supplier"), never taken from the model. A model that omits limitations is flagged (`MODEL_OMITTED_LIMITATIONS`) and the computed uncertainty is still shown.
* **Abstention** is a valid outcome (no claims, nothing wrong): the workflow records it and uses the deterministic fallback.
* **Fallback and traces**: any rejection, abstention, timeout or provider error uses the deterministic stored-data summary; the stage events record the boundary verdict and reasons; the recommendation hash is identical with an agent, a hostile scripted agent, or none (tested).

Evaluation: 28 scripted outputs (accepted, abstained, rejected) with expected verdicts and codes written before the rules were run; 28/28 exact, 0 false accepts, 0 false rejects; one mutant per rule, 10/10 killed. **These outputs are test doubles, not language-model outputs**; they show what the boundary does with any output of these shapes, not how a model behaves. The live test (`tests/test_growth_model_live.py`) is implemented and skipped here with an explicit reason; the gate lists it as unverified.

How to run it where a local model exists: `ollama serve`, pull a model, then `NASHA_LIVE_MODEL_PROVIDER=ollama AP_OLLAMA_MODEL=<model> python -m pytest tests/test_growth_model_live.py`. It asserts the recommendation is unchanged and the verdict is recorded; it makes no claim about quality.

## 2. Supplier intelligence (`growth/supplier_intel.py`, migration 110)
* **Structured provenance**: `supplier_sources` (kind, https URL, the claim it supports, `access` = `page_read` or `search_snippet`, observed date), tenant-scoped, RLS, audit-guarded; the schema refuses non-https URLs and any phone number or e-mail in a claim.
* **Information categories** (from stored status): verified from public sources, unverified public-search lead, synthetic fixture, stale. **Price categories**: published price, supplier quote, synthetic quotation, none published. Quote comparison reports the cheapest **within** a category only; categories are never ranked together; expired quotes and unpriced suppliers are listed, not compared. Founder assumptions stay in project assumptions and are never mixed into supplier comparisons.
* **Rule-based** duplicate detection (same official domain, or the same distinctive words once legal suffixes, plurals and generic words are ignored, with typo tolerance), category classification (weighted keywords), and service-area matching to the project's metro. `add_supplier` refuses a probable duplicate unless a person confirms it is distinct; the refusal is audited.
* **Real-world research performed (2026-10-23, public search only; nobody contacted)** on the three real leads (Farm to Table LLC, Hill Country Dairies, Brothers Produce): directory listings, press and investor profiles were found and recorded as dated sources, **all as search-result snippets (the pages could not be opened from this environment)**. **No official website was found for any of them**, so none is verified, none has a contact channel, none has a published price, and all three remain `lead_unverified`. A finding records this absence (weak evidence, stated as such). Third-party directories showed phone numbers; they were deliberately not stored.
* Evaluation (labelled by the author): dedupe 22 cases precision 1.0 / recall 1.0; classification 16/16; service area 14/14; quote-category separation 5/5; 11 mutants, 11 killed. Honest note: the first run of the dedupe rule produced 2 false positives (names sharing a distinctive prefix); the rule was replaced by a stricter distinctive-word comparison and cases were added, so the final figures are on a set that was extended after seeing a failure. The sets are small and test the stated rules, not the real supplier market.

## 3. Financial model (`growth/financials.py`)
Start-up requirement = capital items (build-out, equipment, furniture, technology, other) + pre-opening costs (licences, deposits, professional fees, training, launch marketing, other) + working capital (months of fixed costs + weeks of opening inventory at the modelled cost of goods) + contingency % of that subtotal, compared with the stated budget (headroom or funding gap). Also gross and contribution margin, break-even, payback, a break-even grid over price and cost changes, sensitivity, and the supplier price effect. Every result is calculated from stored inputs, labelled simulated, shown with formulas and the stored numbers substituted, and listed with its limitations. Inputs that cannot give a defensible number (NaN, infinite, negative costs, out-of-range percentages, positive elasticity) are refused, never computed. Five hand-worked cases match to the cent; 9 mutants, 9 killed. The flagship's placeholder plan needs about $748k against a $600k budget: a funding gap, which is the planning finding the workflow then lets an owner act on.

## 4. The end-to-end workflow
One project, one set of persistent records, twelve steps across roles over HTTP (`tests/test_growth_journey.py`, recorded in the evidence): create the project and budget (owner), record research, shortlist and compare suppliers, change an assumption, recalculate start-up costs, save a scenario, generate a procurement recommendation (analyst), hold it for a different person, record the decision (owner), update the project in the same transaction (a completed sourcing milestone, and the stage advances to `roadmap` only when a saved scenario exists, else `financial_plan`), read the audit history. A rejected recommendation changes nothing about the project.

## 5. Security and reliability
Added: concurrent runs with one idempotency key create exactly one run; two simultaneous approvals record once; replays change nothing; one tenant cannot shortlist, read or annotate another's suppliers; every unauthorised write is refused and audited; the database refuses an unaudited write to each of the launch tables; an injected failure after the milestone insert rolls the whole approval back; research failures (unavailable, runtime error, timeout) never change the recommendation. Found and fixed by these tests: the denial helper closed a shared connection; stated minimum orders were falsely rejected as unstored prices; a THE WEIR code leaked into a business-readable audit summary; refused procurement requests and approvals were not in the chained audit log (now they are); the malformed-report path crashed the older claim check; the app never released workflow and agent resources on shutdown (now it does). The router discards a screen's reads that return after navigation (a latent race exposed by new calls).

## 6. Limitations
No language model has run; the boundary is lexical and structural (a clever paraphrase of a false claim can pass); supplier information is leads and synthetic fixtures only; evaluation sets are small and author-labelled; supplier classification and service-area matching are heuristics; the procurement bill of materials exists only for the hospitality flagship (other industries have projects, assumptions, suppliers and scenarios but no procurement recommendation); one PostgreSQL instance and process; remote CI has not run; manual accessibility and cross-browser testing have not been done.
